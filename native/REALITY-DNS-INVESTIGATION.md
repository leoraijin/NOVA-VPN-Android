# Разбор DNS/TLS таймаута TECNO — состояние 26.10.2026

Первичный разбор ниже выполнен без новых тестов. Позже пользователь разрешил диагностику; актуальные результаты и границы исправления находятся в последнем разделе.

## Наблюдение

Физический TECNO Android 15, отдельная `usbtest.completionpreview`, Rust Reality Core: первые IPv4/IPv6 TUN и routing-проверки достигли ожидаемых ответов. На шаге transport hostname bootstrap получен SocketTimeoutException; локальный DNS-стенд зарегистрировал два вопроса. Сообщение SSLHandshakeException: connection closed в общей фикстуре не доказывает первичный TLS отказ: прежний обработчик сохранял последнюю ошибку и не сбрасывал её перед bootstrap.

## Прослеженный путь

Android `NovaVpnService.autoDetectInterfaceControl` сначала вызывает VpnService.protect, затем bindSocket выбранной физической сети. Rust `net_protect::tcp_socket` / `udp_bind` вызывают callback до connect/bind. DNS `lookup_server_host` требует явный bootstrap UDP/IP/direct и параллельно получает A/AAAA; системный DNS этим путём не используется. Явное TLS server_name=localhost в профиле сохраняется отдельно от transport.test и используется в rustls.

В `transport/tcp_tls.rs::resolve_host` существует отдельный путь: при tun_active=true читается глобальный TUN resolver; если он None, выполнение продолжится в системный lookup_host. `app::Running::drop` снимает глобальный resolver, а FFI отдельно управляет защитным callback. Это потенциальное окно жизненного цикла, в котором системное разрешение имён может попасть в собственный TUN. Однако два наблюдавшихся bootstrap-вопроса показывают, что resolver хотя бы для одного обращения был установлен: текущую причину таймаута этим не доказали.

Нельзя исправлять этот участок простой проверкой наличия protect callback: FFI позволяет установить его до rc_start и не ограничивает использование только TUN; такой запрет сломал бы допустимый SOCKS-сценарий. Нельзя глобально запретить системный resolver для всех tun_active: системный TUN без собственного DNS имеет другой контракт.

## Следующий диагностический шаг, когда пользователь вернётся к тестам

В instrumentation добавлен hostnameBootstrapOnly: тот же профиль/стенд проверяется отдельно, до предыдущих stop/start и без полного маршрутизационного набора. Перед шагом сбрасывается последняя ошибка TLS-стенда; при отказе добавляется обезличенный VpnDiagnostics.report. Новый режим физически не выполнен из-за отключения телефона и последующей просьбы отложить тесты.

Сначала нужны результаты отдельного шага и точная фаза отказа (доставка DNS-ответа, открытие TCP, TLS, VLESS echo). Только затем менять runtime. Для устранения окна global resolver потребуются явный контракт external TUN и владение поколением; это отдельно от переноса SNI и не повод ослаблять TLS или обходить VPN. В production Rust ABI/бинарники на основании этой гипотезы не заменялись.


## Проверки возобновлены пользователем: итог 26.10.2026

Пользователь подключил TECNO и явно разрешил продолжить DNS/TLS диагностику. Сначала короткая проверка прошла; полный сценарий выявил дополнительную гонку самого теста: VpnRuntime.connected публикуется до асинхронного появления NotificationManager.activeNotifications. Тест теперь ждёт одно уведомление до прежнего deadline и сразу отклоняет дубликаты; тишина/importance канала по-прежнему проверяются.

Повторения с новыми hostname на каждом старте воспроизвели исходный таймаут. DNS-фикстура отправила ответы на A и AAAA, сервер завершал outer TLS. Уточнённая фаза — TCP connect тестового UID к зарезервированному IP назначения, до его прикладного echo. Идентификатор новой Android VPN-сети был правильным: гипотеза о старом NetworkHandle не подтвердилась. Это не доказательство неисправного DNS, TLS-сертификата или отсутствующего native resolver.

Тестовый Java-клиент теперь ждёт обе публикации NetworkCapabilities и LinkProperties через default NetworkCallback; callback обязательно снимается. Сокеты не привязываются вручную к другой сети, обход маршрутизации не используется. Для сравнения сохранён управляемый polling-контроль. Дополнительное синхронное чтение LinkProperties перед сокетом также давало успешный прогон и могло менять тайминг; поэтому строгий контроль сохраняет прежний порядок без этого чтения. Он снова упал на восьмом цикле, SocketTimeoutException@tcp-connect. На том же основном и тестовом APK callback-вариант прошёл 20/20. Более ранний callback-вариант также прошёл 20/20. Все отрицательные и положительные результаты сохранены — это поддерживает вывод о гонке готовности пробы, но не доказывает отсутствие любых сетевых гонок платформы.

Рекомендация ждать callback-данные согласуется с [документацией Android](https://developer.android.com/develop/connectivity/network-ops/reading-network-state#listen-to-network-events). Это не утверждение, что один TRANSPORT_VPN подтверждает готовность TCP или доступность интернета.

Bootstrap TUN-стенд ограничен UID отдельного тестового APK; остальные приложения телефона не направляются в искусственный echo. Добавлены счётчики DNS A/AAAA запросов/ответов, TCP accept/TLS completion и фазы connect/write/read. Hostname уникален на каждом цикле, поэтому core host cache не подменяет проверку DNS.

Полный локальный JNI/TUN сценарий обоих ядер на сравнительном APK .2 прошёл с новым ожиданием (IPv4/IPv6, правила приложений, базовый reload, FD/TLS/notification проверки). На TECNO возвращён подготовленный отдельный APK .3; на нём ещё 20/20 циклов Rust bootstrap/TUN прошли. Итого 60 успешных callback-циклов в трёх прогонах. Это не 60 физических смен сети, не вся XHTTP .3 матрица и не проверка 16 КБ runtime.

Production Rust и TLS-политика не менялись. Независимый статический вопрос global resolver lifecycle остаётся отдельным не подтверждённым риском. Экран восстановлен к stay_on_while_plugged_in=0, тестовая служба остановлена, метаданные прежнего пакета NOVA совпали с исходными.
